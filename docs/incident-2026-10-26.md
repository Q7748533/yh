# 事故报告：apex 域名静态文件间歇 404（已解决）

**发生**：2026-10-26 19:50 发现
**解决**：2026-10-26 20:02
**影响**：`sitemap-index.xml`、`sitemap-0.xml`、`rss.xml`、`favicon.svg`、`og/*.png` 在 `thepriceaudit.com` 上约 70–90% 返回 404

---

## 一、现象

同一 URL 连续请求会时而 200、时而 404。实测：

| 目标 | 结果 |
|---|---|
| `thepriceaudit.com/sitemap-index.xml` | 10 次：200 ×1，404 ×9 |
| 同上，另一轮 | 10 次：200 ×3，404 ×7 |
| `thepriceaudit.com/og/*.png` | 5 次：200 ×1，404 ×4 |
| `7c111afc.yh-4pn.pages.dev/sitemap-index.xml`（旧部署） | 10 次：全部 200 |

404 的**响应体是空的**，不是站点自己的 404 页——说明不是 Pages 的静态层在返回它。

---

## 二、排除过程

| 假设 | 检验方式 | 结论 |
|---|---|---|
| 边缘缓存了旧 404 | 响应头 `Cache-Control: no-store`、`cf-cache-status: DYNAMIC`；按 URL 清缓存后复测仍 404 | **排除** |
| 本机代理污染 | 全部请求加 `--noproxy '*'` | **排除** |
| IPv6 分流到旧源 | `curl -4` 与 `curl -6` 分别测 | **排除**（IPv4 同样摇摆） |
| DNS 有遗留记录 | Cloudflare API 查 8 条记录：仅 CNAME → `yh-4pn.pages.dev` + MX/TXT | **排除** |
| Worker 拦截 | `/zones/{id}/workers/routes` = 0 条 | **排除** |
| 规则集拦截 | 6 个 ruleset 全部 0 条规则 | **排除** |
| `_redirects` / `_headers` | 无相关条目 | **排除** |
| 构建产物缺文件 | 具体部署 URL 100% 命中 | **排除** |

**关键线索**：404 与 200 的响应头是两套不同画像——

| | 404 | 200 |
|---|---|---|
| `Cache-Control` | `no-store` | `public, max-age=0, must-revalidate` |
| `ETag` | 无 | 有 |
| `x-robots-tag` | 无 | `noindex` |

两套画像说明**边缘在服务两个不同的部署**。

---

## 三、根因

Cloudflare Pages 项目 `yh` 的**生产部署是一个残缺的旧版本** `d4b93d0b`（创建于 2026-10-26T11:54:26Z）：

| 检查项 | d4b93d0b |
|---|---|
| `sitemap-index.xml` | 404 |
| `favicon.svg` | 404 |
| `og/*.png` | 404 |
| 首页是否含 14:05 的 GA 修复 | **否** |

而旧部署 `7c111afc` 是完整的。**边缘在两个部署之间摇摆**，造成时好时坏。

**推断（未证实）**：`d4b93d0b` 创建时间落在一次失败的部署尝试（11:51Z 报凭证错误）之后 3 分钟，很可能是**部署与构建并发**——上传了正在写入的 `dist`，得到一个不完整的部署。

---

## 四、解决

1. 用具备 Pages 权限的 API Token 重新部署 → 生产部署更新为 `c21f4fa3`（2026-10-26T12:00:45Z，`canonical_deployment` 已指向它）
2. 复验：

| 端点 | 结果 |
|---|---|
| `/` `/sitemap-index.xml` `/sitemap-0.xml` `/rss.xml` | 各 3/3 次 200 |
| `/favicon.svg` `/robots.txt` `/og/*.png` | 各 3/3 次 200 |
| IndexNow key、测评页、品类页 | 各 3/3 次 200 |
| `sitemap-index.xml` 连续 15 次 | **15/15 全部 200** |

3. `sitemap-0.xml` 含 14 个 URL，`sitemap-index.xml` 正确指向它
4. 首页确认含 14:05 的 GA 修复

---

## 五、遗留与后续

- **GSC 需重新提交 sitemap**：此前 404 期间 GSC 大概率报「无法抓取」，恢复后要手动重提一次
- **全站缓存清除失败**（令牌缺 Cache Purge 权限）。影响有限：受影响响应本就是 `no-store`
- **令牌已写入 `.env`**（`CLOUDFLARE_API_TOKEN`，已被 `.gitignore` 覆盖），`npm run deploy` 恢复可用

## 六、教训

1. **健康检查必须覆盖静态资源**，只测 `/` 会漏掉 sitemap / favicon / og 全线故障
2. **具体部署 URL 是最好的对照组**：能立刻区分「产物问题」与「路由/域名问题」
3. **响应头画像差异比状态码更能定位**：两套 `Cache-Control`/`ETag` 组合直接暴露了「两个后端」
4. **部署不可与构建并发**：上传正在写入的目录会得到不完整部署，且不会报错
5. **不要用 grep 判断部署成功**：本次一度因为过滤掉 ERROR 行而误以为部署成功
